## 1. 本書の位置づけ

v1 の開発は機能追加とバグ修正の繰り返しで安定せず、「動いているのか壊れているのか分からない」状態に陥った。
本書は **v1 の反省を踏まえ、何を作るか・何を作らないか・どの順で作るかを確定させる** ための文書である。

- 本書が確定したら、これを唯一の正として v2 を新規実装する
- `CLAUDE.md` / `handoff.md` / `system-overview.md` の記載と矛盾がある場合、**本書を優先**する(v1 ドキュメントは実態と乖離しているため)

## 2. v1 の現状分析(なぜうまくいかなかったか)

### 2.1 引き継ぐべき資産 ✅

| 資産 | 内容 |
|---|---|
| **問題データ 534 問** | Supabase 本番 DB(`wcsurvnglqazxlckgxxg`)に投入済み。6 カテゴリ × 24 テーマ。最大の資産であり **v2 でもそのまま使う** |
| DB スキーマ | categories / themes / questions / answer_history / user_profiles の設計は妥当。v2 でも骨格を維持 |
| 問題 SQL 一式 | `docs/questions_*.sql` に全テーマの INSERT 文が残っており、DB を作り直す場合も復元可能 |
| UI フローの知見 | ログイン → ダッシュボード → 演習設定 → 出題 → 結果、という画面遷移は v2 でも踏襲 |

### 2.2 v1 の構造的問題(v2 で必ず解消する)❌

1. **モノリス構造**: 全画面・全ロジックが `App.tsx` 1 ファイル(約 1,800 行)。修正のたびに別の箇所が壊れ、コミット履歴が「fix の応酬」になっていた
2. **フォールバックデータの二重管理**: DB 接続失敗時用のハードコードデータ(DEFAULT_CATEGORIES 等)が実 DB と乖離し、「表示されるが古い/間違っている」バグを量産した
3. **セキュリティがクライアント側のみ**:
   - 管理者判定が `includes('ikeda')` の文字列部分一致 + ロゴ 5 回タップで強制 ON(React state のみ)
   - 1 日 10 問制限が localStorage 管理(リロードや別ブラウザで回避可能)
   - プレミアム判定も `window.confirm` によるデモ有効化
4. **ドキュメントと実態の乖離**: 「Stripe 決済連携完了」と記載されているが実際は未接続、旧 Supabase URL が CLAUDE.md に残存、など。何が本当かをコードから逆読みする必要があった
5. **検証手段の欠如**: テストゼロ。`npm run build` が 13 件の型エラーで失敗したまま気づかれない期間があった(StackBlitz の dev サーバーは型チェックをスキップするため)
6. **DB 側の設定漏れ**: `user_profiles` の GRANT 漏れにより、プロフィール保存・プレミアム状態保存がサイレントに失敗していた疑い(`docs/fix_user_profiles_permissions.sql` 未適用)

## 3. プロダクト概要

| 項目 | 内容 |
|---|---|
| プロダクト名 | 京都検定 3 級 Web 問題集(仮) |
| 目的 | 京都検定 3 級受験者の合格率向上 |
| 提供形態 | Web アプリ(スマホファースト、PC 対応) |
| ビジネスモデル | フリーミアム(無料: 1 日 10 問 + 広告 / プレミアム: 無制限 + 広告なし) |
| 問題数 | 現在 534 問 → 目標 500 問以上を維持・品質改善 |

### 成功指標(案)

- 学習継続率: 週 3 日以上利用するユーザーの割合
- 全 534 問のうちユーザーが到達できる問題の割合(v1 では「問題準備中」で行き止まりになるテーマがあった)
- プレミアム転換率(収益化フェーズ以降)

## 4. ユーザー種別と権限

| 種別 | 認証 | できること |
|---|---|---|
| 未ログイン(ゲスト) | なし | ランディングページ閲覧のみ(演習はログイン必須)※お試し演習の提供は未決事項 U-3 |
| 無料会員 | Supabase Auth | 1 日 10 問まで演習可 / 広告表示あり / difficulty 1-2 のみ |
| プレミアム会員 | Supabase Auth + サブスク有効 | 無制限演習 / 広告なし / 全難易度(is_premium 問題含む) |
| 管理者 | Supabase Auth + `user_profiles.is_admin` | 管理画面(ユーザー一覧・統計・問題管理) |

**v1 からの変更点**: 管理者・プレミアムの判定は必ず **DB(RLS ポリシー)側で担保** する。クライアント側の判定は表示出し分けのみに使う。

## 5. 機能要件

優先度: **[MVP]** = Phase 1 で必須 / **[P2]** = Phase 2 / **[P3]** = 収益化フェーズ

### F-1 認証 [MVP]

- F-1-1: Google OAuth ログイン(Supabase Auth)
- F-1-2: メール Magic Link ログイン
- F-1-3: ログアウト
- F-1-4: 初回ログイン時に `user_profiles` を自動作成(DB トリガーで実施。v1 のクライアント upsert 方式は廃止)
- 受け入れ基準: ログイン → リロード → セッション維持されている / 別アカウント切替時に前ユーザーのデータが見えない

### F-2 演習(出題)機能 [MVP]

- F-2-1: **テーマ別演習** — カテゴリ → テーマを選んで出題
- F-2-2: **カテゴリ別演習** — カテゴリ単位でまとめて出題(複数カテゴリ選択可)
- F-2-3: **総合演習** — 全問題からランダム出題
- F-2-4: 演習条件設定 — 出題数(10 / 20 / 50 / 全問)、難易度(すべて / 1 / 2 / 3)
- F-2-5: 出題画面 — 4 択 → 回答 → 正誤 + 解説表示 → 「次へ」ボタンで進む(自動進行は実装しない)
- F-2-6: 途中終了 — 演習を中断してダッシュボードに戻れる(確認ダイアログあり)
- F-2-7: 結果画面 — 正答数 / 正答率 / 間違えた問題の一覧と解説
- 受け入れ基準: 全 24 テーマで演習が開始でき、「問題準備中」の行き止まりが存在しない(問題 0 件のテーマはそもそも表示しない)

### F-3 学習履歴・進捗 [MVP]

- F-3-1: 回答を `answer_history` に保存(v1 では 0 件のまま放置されていた。**v2 では MVP に含める**)
- F-3-2: ダッシュボードに累計回答数 / 累計正答率 / 本日の回答数を表示(DB 集計。localStorage は使わない)
- F-3-3: カテゴリ・テーマ別の正答率表示 [P2]
- F-3-4: 弱点分析(正答率の低いテーマの提示) [P2]

### F-4 復習機能 [P2]

- F-4-1: 間違えた問題だけを出題する「復習演習」(`answer_history` から導出。v1 の localStorage 方式は廃止)
- F-4-2: 正解したら復習対象から外れる

### F-5 利用制限(フリーミアム) [MVP は仕組みのみ / 課金は P3]

- F-5-1: 無料会員は 1 日 10 問まで。判定は **DB 側**(answer_history の当日件数を RPC で集計)で行い、クライアントは表示のみ
- F-5-2: 上限到達時にプレミアム案内モーダルを表示
- F-5-3: `is_premium` フラグ付き問題は無料会員には出題しない(RLS で SELECT 自体を制限)

### F-6 決済(プレミアム) [P3]

- F-6-1: Stripe Checkout による月額サブスクリプション(金額は未決事項 U-2)
- F-6-2: Webhook で `subscriptions` を更新し、`user_profiles.is_premium` に反映(Supabase Edge Functions)
- F-6-3: 解約導線(Stripe Customer Portal)
- **注**: v1 のような「デモ有効化」フォールバックは実装しない。未接続の間はプレミアム導線自体を非表示にする

### F-7 広告 [P3]

- F-7-1: 無料会員にのみ Google AdSense を表示(結果画面下部など、演習の邪魔にならない位置)

### F-8 管理機能 [P2]

- F-8-1: 管理者ダッシュボード(ユーザー数・回答数などの統計)
- F-8-2: 問題の CRUD(現在の「SQL を手で流す」運用からの脱却)
- F-8-3: 管理者判定は `user_profiles.is_admin` + RLS。ロゴ連打などの隠し機能は実装しない

## 7. データ要件

### 7.1 既存 DB の扱い

- Supabase プロジェクト `wcsurvnglqazxlckgxxg` と 534 問のデータを **継続利用**する(移行コストゼロ。作り直すのはアプリ側のみ)
- 着手前に以下を実施:
  1. `docs/fix_user_profiles_permissions.sql` の適用(既知の GRANT 漏れ解消)
  2. 全テーブルのスキーマ・RLS ポリシーを実 DB からダンプし、`docs/schema.sql` としてリポジトリに保存(**DB の状態をコードで管理する第一歩**)

### 7.2 スキーマ(v1 から維持 + 変更点)

- `categories`(6 件) / `themes`(24 件) / `questions`(534 件): 現行のまま
- `answer_history`: 現行のまま。**v2 で実際に書き込む**
- `user_profiles`: `is_admin BOOLEAN DEFAULT FALSE` を正式カラムとして追加(v1 はコード側の文字列判定だった)
- `subscriptions`: P3 で Stripe 連携時に作成
- `correct_answer` は 0=A, 1=B, 2=C, 3=D、`difficulty_level` は 1=基礎, 2=応用, 3=上級(v1 踏襲)

### 7.3 RLS 方針(v1 の反省の中核)

| テーブル | ポリシー |
|---|---|
| categories / themes | 全員 SELECT 可 |
| questions | `is_premium = false` は全員 SELECT 可。`is_premium = true` はプレミアム会員のみ |
| answer_history | 本人のみ SELECT / INSERT |
| user_profiles | 本人のみ SELECT / UPDATE(`is_premium`, `is_admin` はクライアントから更新不可) |
| 管理系 | `is_admin = true` のユーザーのみ |

## 8. 非機能要件

### 8.1 セキュリティ

- API キー(anon key)は `.env`(`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`)で管理し、**ソース直書き禁止を今度こそ守る**(v1 は supabaseClient.ts に直書きだった)
- 権限・制限の判定はすべてサーバー側(RLS / RPC / Edge Functions)。クライアントは UI の出し分けのみ
- 隠しコマンド・デバッグ用バックドア(ロゴ連打等)は本番コードに入れない

### 8.2 品質・保守性

- **1 ファイル 1 コンポーネント**。`components/` `hooks/` `lib/` `types/` に分割(CLAUDE.md の推奨構成に準拠)
- TypeScript strict。`any` の常用禁止(v1 は user が `any` だった)
- **フォールバックデータは持たない**。DB 接続失敗時は「エラー画面 + 再試行ボタン」を出す(古いデータを見せるより誠実で、二重管理バグの根を断つ)
- Vitest + React Testing Library で最低限のテスト(出題ロジック・正誤判定・制限判定)
- GitHub Actions で push ごとに `tsc && build && test` を実行(「ビルドが壊れたまま気づかない」の再発防止)

### 8.3 UI/UX

- スマホファースト(375px〜)、PC は中央寄せ最大幅
- ピュア CSS 継続(Tailwind 不使用、v1 方針踏襲)。ただし CSS もコンポーネント単位に分割
- 回答後の自動進行はしない(「次へ」ボタン方式)

### 8.4 開発・運用フロー

- **GitHub main が唯一の正**(v1 と同じ)。StackBlitz は動作確認用
- デプロイ先は Vercel(または Netlify)を想定 [P2、未決事項 U-4]

## 11. フェーズ計画

### Phase 1: MVP(まずここまでを一気に作る)

1. DB 整備(fix SQL 適用、スキーマダンプ、is_admin カラム追加、RLS 見直し)
2. プロジェクト骨格(env 化、ディレクトリ構成、CI、テスト基盤)
3. 認証(F-1)
4. 演習機能一式(F-2)+ 履歴保存・統計(F-3-1, F-3-2)
5. 1 日 10 問制限の DB 側実装(F-5-1, F-5-2)

**Phase 1 完了の定義**: 実アカウントでログインし、全テーマで演習でき、履歴が DB に残り、翌日リロードしても統計が正しい。CI がグリーン。

### Phase 2: 学習体験の強化

- 復習機能(F-4)、テーマ別正答率・弱点分析(F-3-3, F-3-4)、管理画面(F-8)、本番デプロイ

### Phase 3: 収益化

- Stripe 決済(F-6)、is_premium 問題の RLS 制御(F-5-3)、AdSense(F-7)
